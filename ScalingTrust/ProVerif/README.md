# ProVerif in Lean

[ProVerif](https://bblanche.gitlabpages.inria.fr/proverif/) verifies
cryptographic protocols in the symbolic model: a protocol is a process in a
variant of the applied pi calculus, the attacker is Dolev–Yao, and a query asks
for secrecy or for a correspondence between events. This folder embeds that
calculus in Lean so that ProVerif models, among them the ones Noise Explorer
generates for the Noise handshakes, can be reasoned about in Lean. It has three
parts, each a subfolder with its own README.

| Subfolder | What it is |
| --- | --- |
| `TraceSemantics/` | A shallow semantics of the calculus: a process is the set of traces it can perform, the attacker is the set of traces the Dolev–Yao rules allow, and secrecy and correspondence are properties of the attacks on a process. Translated models are written in it and proofs about them are proofs in it, by the methods of `Proofs/` there; `Examples/` there proves the secrecy query of the Denning–Sacco model translated in `Translation/Examples/` and refutes every query of the Noise Explorer `NN` model translated there, by two attacks. |
| `Specification/` | ProVerif itself, deeply: the syntax and operational semantics of its calculus, with terms with effects, as the write-up restates them from the manual's Appendix B, and the adversary and the properties of its queries from the survey, to which the manual refers for them; the denotation of a process as a set of traces; and the proofs that the two semantics agree on secrecy and correspondence, the theorems of the write-up. |
| `Translation/` | A translator from a fragment of ProVerif's input language to Lean source over `TraceSemantics/`, following the recipe its README records: a parser written with `Std.Internal.Parsec` reads the model and Lean's pretty printer writes the translation. `Examples/` there holds two models with their translations and the translations of Noise Explorer's `NN` and `XX` models, which the build checks. |
| `TamarinTranslation/` | A translator from a fragment of Tamarin's input language to Lean source over `TraceSemantics/`, through its `Rewriting.lean`, which reads a multiset rewriting system as a process of the trace semantics: each rule is the set of its instances, and a lemma a property of the attacks on the process of the rules. The algebra of a model is emitted by the ProVerif translator, which it imports; the rules, restrictions and lemmas are its own. Nothing is proved about it yet. `Examples/` there holds the Tamarin manual's initial example and a second model, with their translations, which the build checks. |
| `Writeup/` | `Semantics.tex`, the mathematical account in three sections: the trace semantics, which `TraceSemantics/` formalises; the calculus of ProVerif with the manual's semantics, which `Specification/` formalises; and the translation of the calculus into the trace semantics with the correspondence theorems, the denotation in `Specification/` and the program in `Translation/`. Its PDF is tracked; rebuild it with `pdflatex` after editing the source. |
| `OldWriteup/` | A copy of `Writeup/` as it stood at commit `c09a44d`, before the framework was extended to more features, kept to be polished on its own while `Writeup/` follows the extension. Only a task that names it touches it: do not bring it in line with `Writeup/` or with the code, and do not delete it. |
| `Reference/` | The survey, the manual, the papers the design draws on and two models generated by Noise Explorer; its README says what each file is. |

The subfolders are not independent of one another, unlike the folders under
`ScalingTrust/`. `Specification/` imports `TraceSemantics/`, `Translation/`
emits code against it, and `TraceSemantics/Examples/` imports the translated
models in `Translation/Examples/` to prove or refute their queries;
`Specification/` and
`Translation/` do not depend on each other: the translator does not go through
the syntax of `Specification/`, since the point of the shallow embedding is that
a translated model is ordinary Lean. `TamarinTranslation/` imports
`Translation/`, for its token parsers and for the emission of the algebra of a
model, and emits code against `TraceSemantics/` through its own
`Rewriting.lean`.

## Sources

The folder is built from ProVerif's own documentation and from the papers it
refers to, by four principles, in order of importance:

1. The formal semantics of ProVerif's input language in Appendix B of the
   ProVerif manual (`Reference/proverif-manual.pdf`) is the ground truth for
   what ProVerif code means: `Specification/` and §2 of the write-up state it.
   It takes precedence over the manual's informal chapters where the two
   differ, as they do on whether `&&` and `||` evaluate their second operand
   (§3.1.4 against Appendix B), and over the tool: ProVerif's resolution
   procedure, the encodings it applies to a model beforehand (§4.1.4) and the
   results it reports approximate Appendix B and are never consulted.
2. Where the manual refers to a paper for a component, that paper is the ground
   truth for the component. The manual describes the attacker and the
   properties its queries test informally and refers to Blanchet's survey
   (`Reference/BlanchetFnTPS16.pdf`) for their definitions, so the adversary
   and the basic correspondences are the survey's Definitions 3.1, 3.4 and
   3.5; what the survey does not define, the attacker and message facts and
   the nested and injective correspondences, follows the manual's descriptions
   (§4.3.1), as the write-up's Definition "Correspondences" says. Secrecy
   is the one exception: it is the reachability of the attacker's knowledge
   of the term, which is what ProVerif decides for `query attacker(M)`, and
   not the survey's output on a public name (Definitions 3.2 and 3.3), whose
   strict reading makes every term secret in a model whose public channel is
   a constant; the Specification README says why.
3. The attacker is the abstract Dolev–Yao attacker: an adversary process in the
   specification, and the closure of its knowledge under its operations in the
   trace semantics. Nothing is taken from ProVerif's resolution process, its
   Horn clauses and `attacker` predicate, which overstates the attacker's
   knowledge.
4. Where a source's semantics has to cover syntax it does not have, as the
   survey's adversaries do for the manual's terms with effects, it is extended
   in the natural way, and each nontrivial decision is documented in the code:
   in the README of its folder or in the docstring nearest it.

## Building

The folder depends on Mathlib, pinned in the root `lakefile.toml`; fetch it with
`lake exe cache get`. `ScalingTrust/ProVerif.lean` imports every module of the
folder and is part of the default target, so `lake build` builds it and CI
checks it;

```sh
lake build ScalingTrust.ProVerif
```

builds the folder alone.
