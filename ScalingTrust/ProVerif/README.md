# The process calculus behind ProVerif, as trace sets

A trace-based semantics for the calculus of Blanchet's survey *Modeling and
Verifying Security Protocols with the Applied Pi Calculus and ProVerif* (FnTPS
2016, Fig. 2.4), kept as simple as possible while still able to state ProVerif's
queries. The embedding is shallow: a process is the set of traces it can
perform, what a process computes between actions is ordinary Lean code, and the
attacker is not a program but the set of traces the Dolev–Yao rules allow.

This folder depends on Mathlib (pinned in the root `lakefile.toml`; fetch it
with `lake exe cache get`). It is not part of the default target yet; build it
with

```sh
lake build ScalingTrust.ProVerif.Examples
```

## The semantics

**Actions.** `Act M` has `out c m`, `inp c m`, `new n` and `event e`, over an
abstract message type `M`. The name created by `new n` is `Names.nonce n`; the
semantics needs to know nothing else about messages.

**Processes.** `Proc M` is `Set (List (Act M))`; every process built here is
prefix-closed, so a trace is an execution so far and a process that blocks
simply has no longer traces. `Proc.out`, `Proc.inp`, `Proc.new` and
`Proc.event` prepend an action and `Proc.nil` is `0`. A process can also be
written as a `do` block in the continuation monad `Cont (Proc M)` with
`Proc.send`, `Proc.recv`, `Proc.fresh`, `Proc.emit`, `Proc.fork`, `Proc.repl`
and `Proc.stop`, closed with `Proc.run`; the Lean code between the actions is
the honest computation (ProVerif's `let`, `if` and destructor applications).

**Parallel composition.** `Merges f t`, an inductive relation, says that the
trace `t` arises from the family of component traces `f : ι → List (Act M)` by
interleaving, except that an output of one component and a matching input of a
*different* component may meet in a communication, the survey's rule (Red I/O),
which leaves nothing in `t`. `Proc.merge` lifts it to processes; `Proc.par` is
the merge over `Fin 2` and `Proc.bang` the merge over `ℕ` (a derivation is
finite, so only finitely many copies act). `Proc.bang_eq`, `!P = P | !P`, is
(Red Repl); it rests on `Merges.split` and `Merges.join`, which relate a merge
over `ℕ` to a merge of component `0` with the merge of the rest.

**Completed communications.** `out` and `inp` are offers. A trace with no
unfinished action (`Act.Unfinished`) is one in which every offer met a partner,
and then `Merges.out_of_inp` says that whatever one component received, another
component sent.

**The attacker.** `Attacker M` supplies a closure operator `derive` on `Set M`,
what can be deduced from a set of known messages; `Attacker.ofOps` builds one
from a set of public partial operations, which is ProVerif's `attacker`
predicate for a term algebra. `Enemy K₀ e K` is the most general intruder as a
trace relation: knowing `K₀`, it may receive on any channel it can derive
(learning the message), send anything it can derive on any channel it can
derive, and create names, and it ends up knowing `K`.

**Runs and queries.** `Run P K₀ t e w K` holds when `t ∈ P`, `Enemy K₀ e K`,
`Merges ![t, e] w`, no action of `w` is unfinished, and the nonce indices of `w`
are distinct. This is ProVerif's `P | Q` for every adversary `Q` at once.
`Secret P K₀ s` says that in no run can the attacker end up deriving `s`
(`query attacker(s)` fails). `Corr P K₀ Pre R` says that in every run each
`event ev` with `Pre ev` is preceded by some `event ev'` with `R ev ev'` (a
non-injective `query event(e) ==> event(e')`). `Run.derive_subset` is the
closed-set method for secrecy: a `derive`-closed set that contains the
attacker's initial knowledge, every nonce and every message the protocol offers
bounds everything the attacker can ever derive. `Examples.hashed_secret` uses
it; `Examples.leak_attack` exhibits a run instead.

## Design decisions

* **Synchronous.** Communication is a rendezvous, as in the survey, not
  ProVerif's Horn-clause approximation in which outputs are persistent facts.
  A single sequential process cannot communicate with itself: the two partners
  must be distinct components, which is why the pairing is certified inside
  `Merges` rather than read off adjacent actions of a trace.
* **A communication leaves no action.** A query can observe the events of a run
  and the attacker's final knowledge, and nothing else; what was communicated is
  recoverable from the component traces when a proof needs it.
* **The attacker is semantic.** A Lean function used as an adversary could
  pattern-match on ciphertexts, so functions as adversaries are unsound. The
  attacker is instead the trace set `Enemy`, parametrised only by `derive`.
* **Channels are uniform.** Nothing marks a channel public or private: a
  private channel is a term the attacker cannot derive, on which `Enemy` makes
  no offers.
* **Freshness by index.** Rather than "the new name occurs nowhere", a run
  requires the indices of all its `new`s to be distinct. An instance must keep
  `Names.nonce` out of the attacker's initial knowledge, and honest code must
  not mint nonces by hand.

## Not modelled

Tables (`insert` and `get`; the ProVerif manual, §6.7.3, encodes them with
private channels), phases (runs are ordered, so ordering constraints can be
stated directly), injective correspondences, and queries with `attacker(M)`
among the premises. The Noise Explorer models in `Reference/` use tables,
phases and such mixed queries, so they mark what remains. The `par` example in
`Process.lean` is currently left as `sorry`, pending an inversion principle for
two-component merges.
