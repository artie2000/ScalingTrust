# The process calculus behind ProVerif, as trace sets

A trace-based semantics for the calculus of Blanchet's survey *Modeling and
Verifying Security Protocols with the Applied Pi Calculus and ProVerif* (FnTPS
2016, Fig. 2.4) and for the security properties of ProVerif's queries, as the
target of a translation from ProVerif models. The embedding is shallow: a
process is the set of traces it can perform, what a process computes between
actions is ordinary Lean code, and the attacker is not a program but the set of
traces the Dolev–Yao rules allow.

This folder depends on Mathlib (pinned in the root `lakefile.toml`; fetch it
with `lake exe cache get`). It is not part of the default target yet; build it
with

```sh
lake build ScalingTrust.ProVerif.Examples
```

## Translating a ProVerif model

A model is translated piece by piece, types erased as in the survey's semantics.
`ProVerif.DH` and `ProVerif.Examples` follow this recipe for the survey's running
example.

1. **Free names** (`free a`) become nullary constructors, `DH.Fun.const a` over a
   type of the model's free names; `Theory.Msg.name n` is reserved for the nonces that
   `new` creates.
2. **Constructors** (`fun`, `const`) become the symbols of a signature `F : Sig`.
3. **Equations** (`equation`) become a `Theory F`: the equations `E`, and the
   symbols declared *free*, every symbol that is not at the root of a side of an
   equation (`Theory.heads`, proved by `rfl`). `T.Msg`, terms modulo `E`, is the
   message type, and Lean's `=` on it is the survey's `=_E`.
4. **Destructors** (`reduc`) become Lean functions to `Option T.Msg`, `none`
   being `fail`. Each rewrite rule becomes a function to `Option (Option T.Msg)`:
   `none` when its patterns do not match, `some r` when they do, with `r` the
   right-hand side and `r = none` for `fail`. A pattern over a free symbol is a
   `match` on `Theory.Msg.view` of the argument, a nested pattern a nested match,
   and a repeated variable an equality test. The destructor is the rules in
   order, chained with `<|>` and flattened by `Option.join`, so that the first
   rule that matches decides, even when its result is `fail`, and the result is
   `fail` when none does. With a single rule this is a `match` with a final
   `none`, as in `ProVerif.DH`. A destructor whose rules have no may-fail
   variable is written on messages and lifted by `liftFail`; one with may-fail
   variables takes `Option T.Msg` arguments directly.
5. **Public and private** declarations complete a `MsgAlgebra F`, the theory
   extended by `pubFun`, the public constructors, including the public free
   names, and `pubDtors`, the public destructors.
6. **The process** becomes a `do` block in `Cont (Proc T.Msg)`, closed with
   `Proc.run`: `out` is `Proc.send`, `in` is `Proc.recv`, `new` is `Proc.fresh`,
   `event` is `Proc.emit`, `P | Q` is `if ← Proc.fork then P else Q`, `!P` is
   `Proc.repl` followed by `P`, and `0` is `Proc.stop` or the end of the block.
   `Proc.fork` and `Proc.repl` capture the rest of the block: whatever follows
   them runs in both branches, or in every copy, so they end the block, and so
   does a call to a helper that uses them.
   `let x = D in P else Q` is a Lean `match` on the destructor's result, and
   `if M = N then P else Q` a Lean `if` on the equation of messages. The process
   never uses `Theory.Msg.name`.
7. **Queries** become the security properties they check: `query attacker(M)`
   is `Proc.Secret`, for `M` without nonces; `query F ==> H`, for single facts
   `F` and `H`, is `Proc.Corr F H` with `F` and `H` written as functions of a
   valuation of the query's variables, the survey's Def. 3.5; `attacker(M)` is
   `Fact.knows`.

## The semantics

**Actions.** `Act M` has the offers `out c m` and `inp c m`, the completed
communication `comm c m`, `new n`, whose name is `Names.nonce n`, and `event e`.
The offers are the unfinished actions (`Act.Unfinished`); a trace with none is
one in which every offer met a partner. Processes are written for any message
type `M` with `Names M`, and the attacker and the security properties for any
closure operator `derive` on `Set M` besides; a translated model with algebra
`A` uses `A.Msg` and `A.derive`.

**Processes.** `Proc M` is `Set (List (Act M))`; every process built here is
prefix-closed (Mathlib's `Descriptive.tree`; `aesop` proves it of a translated
`do` block, as `Examples.system_mem_tree` shows, and `Proc.merge_mem_tree` of a
merge), so a trace is an execution so far and a process that blocks has no
longer traces. `Proc.out`, `Proc.inp`, `Proc.new` and
`Proc.event` prepend an action and `Proc.nil` is `0`; `Proc.new` creates a
name that the rest of the process does not create again. The `do`-notation of
step 6 is built from these in the continuation monad.

**Parallel composition.** Two stages. First the component traces
`f : ι → Trace M` are interleaved into a tagged trace `s : TaggedTrace ι M`:
`s.Interleaves f` says that each component reads its own trace back off `s` by
projection.
Then `s.Comms t` says that `t` is obtained from `s` by letting an output
immediately followed by a matching input of a *different* component meet in a
communication, the survey's rule (Red I/O), which the trace records as `comm`.
`Proc.merge` combines the two and keeps only the traces whose created names are
distinct, so that different components never create the same name; `Proc.par`
is the merge over `Fin 2` and `Proc.bang` the merge over `ℕ` (a trace is
finite, so only finitely many copies act). `Proc.bang_eq`, `!P = P | !P`, is
(Red Repl).

**Messages.** `Theory.Msg.view` shows a message's head symbol and arguments when the
symbol is free and nothing otherwise, and `Theory.view_congr` proves it
invariant under `E`, so a destructor matching on the view is a function on
messages. This deviates from the survey, which matches rewrite rules modulo `E`;
the head of `Term.lean` says why the two agree for every destructor that can be
written. A predicate on messages has to respect `E`; `Theory.Satisfies.lift` produces one
from any structure that satisfies the equations, and that is how the closed
sets of secrecy proofs are defined.

**The attacker.** For a message algebra `A` the attacker is the Dolev–Yao
attacker: what it can deduce from a set of messages, `A.derive`, is the least
superset closed under the public operations `A.ops` (`deriveOfOps`),
ProVerif's `attacker` predicate (survey §3.2.2); an argument may be `fail`
(`none`), which the attacker can always write. `Enemy derive K` is the most general
intruder as a process: knowing `K`, it may receive on any channel it can derive
(learning the message), send anything it can derive on any channel it can
derive, to the protocol or to itself, and create names. `t.attackerKnowledge K` reads its knowledge off a
trace: a message communicated on a channel it knew at the time becomes known,
whoever received it.

**Attacks and security properties.** `P.Attacks` is the process of traces of
`P | Enemy ∅` in which no action is unfinished: ProVerif's `P | Q` for every
adversary `Q` at once. A prefix of an attack is an attack
(`Proc.attacks_mem_tree`), so a property of every attack is a property of
every point of every attack. The facts of a query, `Fact`, are events and
`knows m`, and `Fact.Holds` says whether one holds after an attack.
`P.Secret derive s` says that in no attack does the attacker come to know `s`.
`P.Corr derive F H` says that in every attack in which an instance `F σ` holds,
`H σ'` holds for some `σ'` with `F σ' = F σ`, so by the time `F σ` does. `Proc.secret_of_closed` is the closed-set method for
secrecy: a `derive`-closed set that contains every nonce, and that the protocol
never leaves as long as it receives only messages in it (`Trace.Bounded`),
bounds everything the attacker can ever know. `Examples.hashed_secret` uses it;
`Examples.leak_attack` exhibits an attack instead.

## Design decisions

* **Synchronous.** Communication is a rendezvous between two distinct
  components, the survey's (Red I/O), not ProVerif's Horn-clause approximation
  in which outputs are persistent facts. It is therefore defined on the tagged
  interleaving, where the components are still known.
* **A communication is an action.** A completed communication is recorded as
  `comm c m`. The attacker's knowledge is read off these actions, and they keep
  an exchange apart from an `out` directly followed by a matching `inp` that
  are two unmatched offers, as in the trace of `out(c, m); in(c, x)`. The
  attacker, being one component, also performs `comm c m` on its own: an output
  to itself, which the survey's Def. 3.2 counts as a public output when `c` is
  public.
* **The attacker learns by listening.** `Trace.attackerKnowledge` counts a message as known once
  it is communicated on a channel the attacker knows at the time, whoever
  received it. The attack does not record the receiver: the attacker could
  have received the message instead, and the survey's Def. 3.2
  and ProVerif's clauses count it the same way. The attacker's own names count
  only once it sends them, to the protocol or to itself, since the trace does
  not say who created a name.
* **Channels are uniform.** Nothing marks a channel public or private: a
  private channel is a term the attacker cannot derive, on which `Enemy` makes
  no offers and from which it learns nothing.
* **Free names are constants.** The survey keeps free names apart from
  function symbols, making them public or private through an environment
  `(N_pub, N_priv)`. Here a free name is a nullary constructor, as the ProVerif
  manual treats it (§6.7.3: a free name, a constant and a top-level bound name
  "all declare a constant"), and only the names `new` creates are names. So
  the `MsgAlgebra` alone says what is public, and the attacker starts from `∅`, the public
  free names being derivable from nothing. The survey's Def. 3.2, whose public
  channel must be a name, is the one definition this changes; see `Secret`.
* **Freshness by index.** Rather than "the new name occurs nowhere", the
  indices of all the `new`s in a trace are distinct: `Proc.new` refuses to
  create a name the rest of the process creates again, `Proc.merge` refuses
  traces in which two components created the same name, and `Enemy.new` does
  as `Proc.new`. This is Paulson's `Nonce N ∉ used evs` pushed into the
  constructors, and the applied pi convention that bound names are pairwise
  distinct.
* **Properties of whole attacks.** `Secret` and `Corr` quantify over attacks,
  not over their prefixes. `Attacks` is prefix-closed, so a property of every
  attack holds at every point of every attack; this is how the survey's
  Defs. 3.3 and 3.5 quantify over all traces, and how ProVerif reads
  `F ==> H` as "`H` before `F`", by stopping the execution just after `F`
  (manual §4.3.1).

## Not modelled

Tables (`insert` and `get`; the ProVerif manual, §6.7.3, encodes them with
private channels), phases, queries with more than one fact on a side of `==>`
(conjunctions, disjunctions, nested and injective correspondences) and the
secrecy of bound names (`query secret x`). The Noise Explorer models in `Reference/` use tables and
phases, so they mark what remains.
