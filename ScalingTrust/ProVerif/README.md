# The process calculus behind ProVerif, as trace sets

A trace-based semantics for the calculus of Blanchet's survey *Modeling and
Verifying Security Protocols with the Applied Pi Calculus and ProVerif* (FnTPS
2016, Fig. 2.4), kept as simple as possible while still able to state ProVerif's
queries. The embedding is shallow: a process is the set of traces it can
perform, what a process computes between actions is ordinary Lean code, and the
attacker is not a program but the set of traces the Dolev–Yao rules allow.

This folder depends on Mathlib (pinned in the root `lakefile.toml`; fetch it
with `lake exe cache get`). It is not part of the default target yet; build it
with

```sh
lake build ScalingTrust.ProVerif.Examples ScalingTrust.ProVerif.DH
```

## Modules

| Module | Contents |
| --- | --- |
| `ProVerif.Process` | Actions, processes as trace sets, interleaving and communication, `!P = P \| !P`, `do`-notation |
| `ProVerif.Query` | The attacker as a process, attacks, `Secret`, `Corr`, the closed-set method; the `Names` and `Attacker` instances of a message algebra |
| `ProVerif.Term` | Message algebras built from a signature and equations: terms, the congruence, `Msg`, views, public operations |
| `ProVerif.DH` | An example algebra: the survey's standard primitives with Diffie–Hellman, destructors by pattern matching |
| `ProVerif.Examples` | A toy term algebra, an attack, a secrecy proof |

`Reference/` holds the survey, the ProVerif manual, the two papers cited below
and two models generated by Noise Explorer; its README says what each file is.

## The semantics

**Actions.** `Act M` has `out c m`, `inp c m`, `new n`, `event e` and `say m`,
over an abstract message type `M`. The name created by `new n` is
`Names.nonce n`; the semantics needs to know nothing else about messages.
`say m` is the attacker's declaration that it knows `m`; honest processes never
use it.

**Messages.** The semantics needs nothing more of `M`, but `ProVerif.Term`
constructs the survey's message algebras (§2.1, §2.5.1) from their data. A
signature `F : Sig` gives the constructors of each arity; raw terms are the
terms of that first-order language, Mathlib's `FirstOrder.Language.Term`, with
the names `ℕ` as variables, so a fresh name is a variable and a protocol's free
names are constants. A `Theory F` gives the equations `E` and declares which
symbols are *free*; `Msg T` is the quotient of terms by the congruence `Eqv`
generated by `E`, so Lean's `=` on messages is the survey's `=_E`, and
`Theory.realize_eq` says every instance of an equation is an equality of
messages. `Msg.view` shows a message's head symbol and arguments when the
symbol is free and nothing otherwise; a destructor is a Lean function on
messages returning an `Option`, with `none` for `fail`, written as a `match` on
the view with one branch per rewrite rule in order and a last branch for
failure, a non-linear pattern being an equality test in its branch. `let x = D
in P else Q` is then a Lean `match` on a destructor's result, and `if M then P
else Q` a Lean `if` on a proposition such as `m = tt`; equality on the quotient
is classical. `Pub T` lists the constructors and destructors the attacker may
apply, and `ProVerif.Query` derives the `Names` and `Attacker` instances.

The declaration of free symbols is justified once and for all: a theory must
show that both sides of every equation have a non-free symbol at the root
(`Theory.heads`, decided by `rfl`), and `Theory.view_congr` then proves the view
invariant under `E`. This is where the translation deviates from the survey, as
recorded at the head of `Term.lean`. The survey matches destructor rules against
their arguments modulo `E`, and its `D ⇓ U` is a relation, since several matches
may give different results. Matching on the view sees only the free symbols,
which is the survey's own condition for pattern-matching on data constructors
(p. 35); under it evaluation is a function and the two semantics agree. No
destructor in the ProVerif manual's examples or in Noise Explorer's models has a
pattern over an equated symbol. Types are ignored, as in the survey's semantics.

`ProVerif.DH` is the worked example: the booleans, pairs, symmetric and
asymmetric encryption, signatures, a hash, and Diffie–Hellman exponentiation
with `exp(exp(g,x),y) = exp(exp(g,y),x)`. It declares ten symbols, one
equation, and `exp` as the only non-free symbol, and writes its six destructors
as matches on the view, `| .app .senc a => if a 1 = k then some (a 0) else none`
for `sdec`.

**Processes.** `Proc M` is `Set (List (Act M))`; every process built here is
prefix-closed, so a trace is an execution so far and a process that blocks
simply has no longer traces. `Proc.out`, `Proc.inp`, `Proc.new` and
`Proc.event` prepend an action and `Proc.nil` is `0`; `Proc.new` creates a
name that the rest of the process does not create again. A process can also be
written as a `do` block in the continuation monad `Cont (Proc M)` with
`Proc.send`, `Proc.recv`, `Proc.fresh`, `Proc.emit`, `Proc.fork`, `Proc.repl`
and `Proc.stop`, closed with `Proc.run`; the Lean code between the actions is
the honest computation (ProVerif's `let`, `if` and destructor applications).

**Parallel composition.** Two stages. First the component traces
`f : ι → List (Act M)` are interleaved into a tagged trace
`s : List (ι × Act M)`: `Interleaves f s` says that each component reads its
own trace back off `s` by projection, so interleaving needs no rules at all.
Then `comms s` is the set of traces obtained by letting an output immediately
followed by a matching input of a *different* component meet in a
communication, the survey's rule (Red I/O), which leaves nothing in the trace.
`Proc.merge` combines the two and keeps only the traces whose created names are
distinct, so that different components never create the same name; `Proc.par`
is the merge over `Fin 2` and `Proc.bang` the merge over `ℕ` (a trace is
finite, so only finitely many copies act). `Proc.bang_eq`, `!P = P | !P`, is
(Red Repl); it rests on `Proc.split` and `Proc.join`, which relate a tagged
trace over `ℕ` to one over `Fin 2` whose second component is what the other
copies produce among themselves, their offers to component `0` left unfinished.

**Completed communications.** `out` and `inp` are offers. A trace with no
unfinished action (`Act.Unfinished`) is one in which every offer met a partner,
and then `out_of_inp_comms` says that whatever one component received, another
component sent.

**The attacker.** `Attacker M` supplies a closure operator `derive` on `Set M`,
what can be deduced from a set of known messages; `Attacker.ofOps` builds one
from a set of public operations, each giving the set of its possible results,
which is ProVerif's `attacker` predicate for a term algebra; the instance for
the messages of a theory takes the operations its `Pub` instance declares.
`Enemy K` is the most general intruder as a
process: knowing `K`, it may receive on any channel it can derive (learning
the message), send anything it can derive on any channel it can derive, create
names, and say anything it can derive.

**Attacks and queries.** `Attacks P K` is the process of traces of `P | Enemy K`
in which no action is unfinished. This is
ProVerif's `P | Q` for every adversary `Q` at once. Queries are properties of
the actions of an attack. `Secret P K s` says that in no attack does the attacker
say `s` (`query attacker(s)` fails). `Corr P K Pre R` says that in every attack each
action satisfying `Pre` is preceded by some action related to it by `R`: with
`Pre` picking out events it is a non-injective `query event(e) ==> event(e')`,
and with `Pre` picking out `say M` it is `query attacker(M) ==> event(e')`.
`secret_of_closed` is the closed-set method for secrecy: a `derive`-closed set
that contains the attacker's initial knowledge, every nonce and every message
the protocol offers bounds everything the attacker can ever say, provided the
protocol itself never says anything. `Examples.hashed_secret` uses it;
`Examples.leak_attack` exhibits an attack instead.

## Design decisions

* **Synchronous.** Communication is a rendezvous, as in the survey, not
  ProVerif's Horn-clause approximation in which outputs are persistent facts.
  A single sequential process cannot communicate with itself: the two partners
  must be distinct components, which is why communication is defined on the
  tagged interleaving, where the components are still known, rather than read
  off adjacent actions of an untagged trace.
* **A communication leaves no action.** A query can observe the events of an attack
  and what the attacker says, and nothing else; what was communicated is
  recoverable from the component traces when a proof needs it.
* **The attacker speaks.** An attack does not record what the attacker learnt, so
  its knowledge is made visible by `say`, as with the intruder of Schneider's
  CSP approach: at any time it may say anything it can derive. This is what
  lets `attacker(M)` appear in a correspondence like an event. Honest code must
  not `say`; `secret_of_closed` asks for this explicitly.
* **The attacker is semantic.** A Lean function used as an adversary could
  pattern-match on ciphertexts, so functions as adversaries are unsound. The
  attacker is instead the process `Enemy K`, parametrised only by `derive`.
* **Channels are uniform.** Nothing marks a channel public or private: a
  private channel is a term the attacker cannot derive, on which `Enemy` makes
  no offers.
* **Freshness by index.** Rather than "the new name occurs nowhere", the
  indices of all the `new`s in a trace are distinct: `Proc.new` refuses to
  create a name the rest of the process creates again, `Proc.merge` refuses
  traces in which two components created the same name, and `Enemy.new` does
  as `Proc.new`. This is Paulson's `Nonce N ∉ used evs` pushed into the
  constructors, and the applied pi convention that bound names are pairwise
  distinct. An instance must keep `Names.nonce` out of the attacker's initial
  knowledge, and honest code must not mint nonces by hand.

## Not modelled

Tables (`insert` and `get`; the ProVerif manual, §6.7.3, encodes them with
private channels), phases (attacks are ordered, so ordering constraints can be
stated directly) and injective correspondences. The Noise Explorer models in
`Reference/` use tables and phases, so they mark what remains. The `par` example in
`Process.lean` is currently left as `sorry`; it needs the interleavings of two
one-action traces enumerated.

  deduction relation, in PVS.

  `do`-notation.
