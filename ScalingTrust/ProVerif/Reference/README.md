# Reference material

The sources the ProVerif folder is built from, and the real ProVerif input it
is measured against. Nothing here is built.

| File | What it is |
| --- | --- |

| `proverif-manual.pdf`, `proverif-manual.txt` | The ProVerif manual, with a text extraction for searching. Tables are §4.1.5; their encoding by private channels is §6.7.3. |
| `DutertreSchneider97.pdf` | B. Dutertre and S. Schneider, *Using a PVS Embedding of CSP to Verify Authentication Protocols*, TPHOLs 1997. The same design as this folder, processes as trace sets and an enemy process built from a deduction relation, in PVS. |
| `Claessen99.pdf` | K. Claessen, *A Poor Man's Concurrency Monad*, JFP 1999. The continuation-monad presentation behind the `do`-notation of `ProVerif.Process`. |

## Noise Explorer's ProVerif models

Reference copies of two of the models generated by [Noise
Explorer](https://noiseexplorer.com), taken from the `models/` directory of
[symbolicsoft/noiseexplorer](https://github.com/symbolicsoft/noiseexplorer).
They are kept so that claims about what the embedding must be able to express
can be checked against real ProVerif input rather than against the textbook
encoding. They use a single untyped `key` sort, events, two phases, tables for
per-session state, and queries that mix `attacker` facts with events; the
folder's README lists which of these the embedding does not yet cover.

### Security properties

Compromise is modelled with `event LeakS(phasen, principal)` and the two phases
`phase0`, `phase1`, a key being leaked by `out(pub, key_s(me))`. Queries then
take the form

```
attacker(msg_a(alice, bob, sid_a)) ==>
  event(LeakS(phase0, bob)) || (event(LeakS(px, bob)) && event(LeakS(pz, alice)))
```

so a payload security grade from spec §7.7 becomes a disjunction of compromise
scenarios qualified by phase. These files are therefore also worked examples
(two of Noise Explorer's sixty) of the grade-to-query mapping that
`ScalingTrust.Noise.Security` computes the left-hand side of.

## Comparison with the Noise folder's symbolic model

The rest of this file compares the models with `ScalingTrust.Noise.Symbolic`
and `ScalingTrust.Noise.Crypto`, the Dolev–Yao model of the Noise folder. It is
a cross-folder comparison, kept with the models it is about.

### The Diffie–Hellman fragment

```
const g:key              [data].
fun validkey(key):key.
fun dhexp_real(key, key):key.
equation forall a:key, b:key;
  dhexp_real(b, dhexp_real(a, g)) = dhexp_real(a, dhexp_real(b, g)).
reduc forall b:key;
  dhexp(b, bit2key(zero)) = bit2key(zero);
  forall b:key, k:key;
  dhexp(b, validkey(k)) = dhexp_real(b, k).
```

There is **no** group/exponent type distinction: private keys, public keys and
DH outputs all inhabit the single type `key`, just as they all inhabit `Sym` in
`ScalingTrust.Noise.Symbolic`. The commutativity equation is anchored at the
constant `g`, and so identifies exactly the same pairs of terms that the Lean
model's `Sym.dh_pubKey_eq_iff` characterises.

The correspondence is

| `Sym`       | Noise Explorer                    |
| ----------- | --------------------------------- |
| `pubKey n`  | `validkey(dhexp_real(n, g))`      |
| `dhOut a b` | `dhexp_real(a, dhexp_real(b, g))` |

Both `dhexp` and `Sym.dh` are *partial*: given a second argument that is not a
public key, `dhexp` matches no clause and the process branch dies, and `Sym.dh`
returns `none`, which `mixDH` turns into an `invalidPublicKey` error — kept
distinct from `missingDHKey`, which means a key was never communicated at all.
This is the error-signalling option of spec §4.1.

Note that `dhexp_real(a, X)` for an attacker-chosen `X` *is* reachable in Noise
Explorer, because `validkey` is a public constructor with no destructor and so an
attacker may tag any term. `Sym` cannot express that: `pubKey` is indexed by a
`Nat`, so a key-shaped term with arbitrary contents has no representation here.

### Where the Lean model is weaker

Both differences understate the attacker.

* **No zero key.** `dhexp(b, bit2key(zero)) = bit2key(zero)` models an all-zeros
  Diffie–Hellman output, the low-order-point behaviour of X25519. Nothing in
  `Sym` corresponds, so attacks that force a shared secret to a constant are
  outside the Lean model.
* **No well-formedness tag.** `validkey` is a tag an attacker may apply to any
  term, so Noise Explorer distinguishes a peer sending something key-shaped
  (which yields an opaque DH output) from a peer sending arbitrary bytes (which
  fails). `Sym` has no tag, so both cases fail here.

### Other divergences

* **HKDF is idealised.** The models declare `hmac_hash1`, `hmac_hash2` and
  `hmac_hash3` as three independent free functions, where
  `ScalingTrust.Noise.Crypto` derives the outputs from a single `hmac` by the
  chaining of spec §4.3. Theirs is tractable, ours is faithful; a compiler has
  to choose.
* `hash` is binary (`hash(h, data)`, matching `MixHash`) rather than a unary
  hash composed with concatenation.
* Nonces are an abstract type with `increment_nonce`, not `Nat`.
