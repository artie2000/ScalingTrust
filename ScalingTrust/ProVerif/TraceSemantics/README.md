# The process calculus behind ProVerif, as trace sets

A trace-based semantics for the process calculus of ProVerif, whose meaning the
ProVerif manual fixes (Appendix B), and for the attacker and the security
properties of ProVerif's queries, which the manual refers to Blanchet's survey
for (Definitions 3.1–3.5), as the target of a translation from ProVerif models. The embedding is shallow: a
process is the set of traces it can perform, what a process computes between
actions is ordinary Lean code, and the attacker is not a program but the set of
traces the Dolev–Yao rules allow. It is one of the three subfolders of
`ScalingTrust/ProVerif/`; the README there says how they fit together.

This folder depends on Mathlib (pinned in the root `lakefile.toml`; fetch it
with `lake exe cache get`); `lake build ScalingTrust.ProVerif` builds it with
the rest of the folder.

## The semantics

**Actions.** `Act M` has the offers `out c m` and `inp c m`, the completed
communication `comm c m`, `new n`, whose name is `Names.nonce n`, and `event e`.
The offers are the unfinished actions (`Act.Unfinished`); a trace with none is
one in which every offer met a partner. Processes are written for any message
type `M` with `Names M`, and the attacker and the security properties for any
`M` with an `Attacker M` instance besides, the attacker's operations being
canonical for a type of messages; a translated model declares the instance its
public declarations give.

**Processes.** `Proc M` is `Set (List (Act M))`; every process built here is
prefix-closed (Mathlib's `Descriptive.tree`; `aesop` proves it of a translated
`do` block, as `DenningSacco.system_mem_tree` in `../Translation/Examples/`
shows, and `Proc.merge_mem_tree` of a
merge), so a trace is an execution so far and a process that blocks has no
longer traces. `Proc.out`, `Proc.inp`, `Proc.new` and
`Proc.event` prepend an action and `Proc.nil` is `0`; `Proc.new` creates a
name that the rest of the process does not create again. The `do`-notation in
which translated processes are written is built from these in the continuation
monad. An `Option`, such as a destructor's result, is bound with `←` and stops
the process when it is `none` (`Proc.ofOption`): ProVerif's `let` without
`else`.

**Parallel composition.** Two stages. First the component traces
`f : ι → Trace M` are interleaved into a tagged trace `s : TaggedTrace ι M`:
`s.Interleaves f` says that each component reads its own trace back off `s` by
projection.
Then `s.Comms t` says that `t` is obtained from `s` by letting an output
immediately followed by a matching input of a *different* component meet in a
communication, the manual's communication rule, which the trace records as `comm`.
`Proc.merge` combines the two and keeps only the traces whose created names are
distinct, so that different components never create the same name; `Proc.par`
is the merge over `Fin 2` and `Proc.bang` the merge over `ℕ` (a trace is
finite, so only finitely many copies act). `Proc.bang_eq`, `!P = P | !P`, is
the manual's replication rule.

**Messages.** `Theory.Msg.view` shows a message's head symbol and arguments when the
symbol is free and nothing otherwise, and `Theory.view_congr` proves it
invariant under `E`, so a destructor matching on the view is a function on
messages. This deviates from the manual, whose Figure B.1 applies a rule when
the arguments are equal modulo `E` to an instance of its left-hand side;
the head of `Term.lean` says why the two agree for every destructor that can be
written. A predicate on messages has to respect `E`; `Theory.Satisfies.lift` produces one
from any structure that satisfies the equations, and that is how the closed
sets of secrecy proofs are defined.

The messages of a model are `T.withData.Msg`, for `T` the theory of its
declarations: `Theory.withData` adds the data symbols that ProVerif builds into
every term algebra, a tuple constructor of every arity and the two booleans,
which give the messages their standard operations, the `StdOps` instance.
`Theory.withData_satisfies` says that they still satisfy the equations of `T`,
and `Theory.satisfies_withData_iff` that a structure for the extended signature
satisfies `T.withData` when, read through the inclusion, it satisfies `T`;
`Examples.shape_satisfies` uses it. For protocols written by hand, a product of
messages `(m₁, …, mₙ)` where a message is expected is the `n`-tuple (the class
`Tuple` and the coercion `Tuple.toMsg`), `Tuple.ofMsg (M × ⋯ × M)` reads the
components back, and a `Bool` is the constant `StdOps.ofBool`; the components
of a product are messages, so a nested tuple or a boolean inside one carries
its type, as `((a, b) : M)`. `Examples.swap` is `in(c, (x, y)); out(c, (y, x,
true))` written this way. ProVerif's `=`, `<>`, `not`, `&&` and `||` are
destructors with rewrite rules (manual, Appendix B), not operations of the
message type; a protocol written in Lean tests equality with `if m = n then …
else …`.

**The attacker.** The attacker is the Dolev–Yao attacker: its operations,
each of some arity on may-fail arguments, are the `Attacker` instance of the
message type, and what it can deduce from a set of messages, `Attacker.derive`,
is the least superset closed under them (`deriveOfOps`): the Dolev–Yao
deduction relation, with the operations the survey's `N_pub`-adversaries may
apply (Definition 3.1); an argument may be `fail` (`none`), which the attacker
can always write. `Attacker.ofDecls` builds the instance of a model
from its public declarations, the constructors and free names not marked
`[private]` and the public destructors, together with the standard operations,
`StdOps.ops`: the tuples, their projections and the booleans, which the attacker
always has. `Enemy K` is the most general
intruder as a process: knowing `K`, it may receive on any channel it can derive
(learning the message), send anything it can derive on any channel it can
derive, to the protocol or to itself, and create names. `t.attackerKnowledge K` reads its knowledge off a
trace: a message communicated on a channel it knew at the time becomes known,
whoever received it.

**Attacks and security properties.** `P.Attacks` is the process of traces of
`P | Enemy ∅` in which no action is unfinished: ProVerif's `P | Q` for every
adversary `Q` at once. A prefix of an attack is an attack
(`Proc.attacks_mem_tree`), so a property of every attack is a property of
every point of every attack. The facts of a query, `Fact`, are events and
`knows m`, and `Fact.Holds` says whether one holds after an attack.
`P.Secret s` says that in no attack does the attacker come to know `s`.
`P.Corr F H` says that in every attack in which an instance `F σ` holds,
`H σ'` holds for some `σ'` with `F σ' = F σ`, so by the time `F σ` does.
`Examples.leak_attack` exhibits an attack.

**The closed-set method.** `Proc.secret_of_closed` proves secrecy. A family of
derivation-closed sets `S N`, indexed by the set `N` of the names the protocol
creates in an attack, bounds everything the attacker can ever know, provided
`S N` contains every name outside `N` and the protocol is bounded by `S`
(`Proc.Bounded`): each of its traces sends only messages in `S N`, for every `N`
containing the names it creates, as long as every message it received before
lies in `S N` (`Trace.Bounded`). The attacker's names are the ones outside `N`,
since a merge keeps the names of its components apart
(`TaggedTrace.proj_nonces_disjoint`). `Proc.Bounded` has one rule per
constructor, so a translated `do` block is proved bounded by following it:
`Proc.Bounded.new` adds the name created to `N`, `Proc.Bounded.inp` adds the
message received to `S N`, and `Proc.Bounded.out` asks that the message sent lie
in `S N`. `Examples.system_secret` proves `DenningSacco.query₁`, the translated
Denning–Sacco model's `query attacker(s)`, this way, with `S N` the messages in
which `s` and the names in `N` occur only hashed, under `pk`, encrypted under a
name in `N`, or signed with one and encrypted for one, a tuple being safe when
its components are; `Examples.Shape` is the structure on which that set is
defined so that it respects the equation.

## Design decisions

* **Synchronous.** Communication is a rendezvous between two distinct
  components, the manual's communication rule, and is therefore defined on the
  tagged interleaving, where the components are still known.
* **A communication is an action.** A completed communication is recorded as
  `comm c m`. The attacker's knowledge is read off these actions, and they keep
  an exchange apart from an `out` directly followed by a matching `inp` that
  are two unmatched offers, as in the trace of `out(c, m); in(c, x)`. The
  attacker, being one component, also performs `comm c m` on its own: an output
  to itself, which the survey's Def. 3.2 counts as a public output when `c` is
  public.
* **The attacker learns by listening.** `Trace.attackerKnowledge` counts a message as known once
  it is communicated on a channel the attacker knows at the time, whoever
  received it. The attack does not record the receiver: the attacker could
  have received the message instead, and the survey's Def. 3.2 counts it the
  same way. The attacker's own names count
  only once it sends them, to the protocol or to itself, since the trace does
  not say who created a name.
* **Channels are uniform.** Nothing marks a channel public or private: a
  private channel is a term the attacker cannot derive, on which `Enemy` makes
  no offers and from which it learns nothing.
* **Free names are constants.** The survey keeps free names apart from
  function symbols, making them public or private through an environment
  `(N_pub, N_priv)`. Here a free name is a nullary constructor, as the ProVerif
  manual treats it (§6.7.3: a free name, a constant and a top-level bound name
  "all declare a constant"), and only the names `new` creates are names. So
  the `Attacker` instance alone says what is public, and the attacker starts from `∅`, the public
  free names being derivable from nothing. The survey's Def. 3.2, whose public
  channel must be a name, is the one definition this changes; see `Secret`.
* **Freshness by index.** Rather than "the new name occurs nowhere", the
  indices of all the `new`s in a trace are distinct: `Proc.new` refuses to
  create a name the rest of the process creates again, `Proc.merge` refuses
  traces in which two components created the same name, and `Enemy.new` does
  as `Proc.new`. This is Paulson's `Nonce N ∉ used evs` pushed into the
  constructors, and the applied pi convention that bound names are pairwise
  distinct.
* **Properties of whole attacks.** `Secret` and `Corr` quantify over attacks,
  not over their prefixes. `Attacks` is prefix-closed, so a property of every
  attack holds at every point of every attack; this is how the survey's
  Defs. 3.3 and 3.5 quantify over all traces, and how ProVerif reads
  `F ==> H` as "`H` before `F`", by stopping the execution just after `F`
  (manual §4.3.1).
* **The protocol's names, as a set of indices.** The closed set of a secrecy
  proof is indexed by the set of the names the protocol has created, and
  protects them alike: the index does not say which `new` created a name. A
  name the attacker creates is outside the set and may be known to it.

## Not modelled

Tables (`insert` and `get`; the ProVerif manual, §6.7.3, encodes them with
private channels), phases, queries with more than one fact on a side of `==>`
(conjunctions, disjunctions, nested and injective correspondences) and the
secrecy of bound names (`query secret x`). The Noise Explorer models in `../Reference/` use tables and
phases, so they mark what remains.
